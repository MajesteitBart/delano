# Spec: Delano User Value and Product Quality Gates

## Executive Summary

The failed Kotlin Android app contained 13,673 lines of Kotlin, 6,176 lines of tests, and 3,988 lines of Delano documentation. The finished app could not show one agent message or let Bart respond. It technically passed its own scope. That is the failure this project must prevent.

On the real server, the app listed 342 threads with no transcript, creation, response, or useful supervision workflow. The global Add action always added an environment. Screens showed broken plurals, repeated titles, raw UUIDs, redundant labels, and Unknown fields. The scope had explicitly deferred the user's core actions, then Delano accepted tests, artifacts, and completed tasks as proof of success.

Delano will add three hard decisions:

1. Before a meaningful project starts, it names the user, job, newly possible action, deliberate omissions, and literal steps a reviewer will perform on realistic data.
2. During delivery, a thin working slice comes before broad groundwork. Each checkpoint compares working user actions with the prior result. Any executor can stop when the promised job is unreachable.
3. Before product work closes, a human performs the steps on representative real data and judges usefulness, information hierarchy, copy, contextual actions, data quality, and interaction. Tests and screenshots cannot overrule a failed workflow.

Transport, persistence, reconciliation, recovery, security, integrations, and tests remain valuable. Infrastructure may consist entirely of them. It states that no end-user action changes yet, names the downstream action, and requires an owner decision. Foundation work cannot quietly stand in for a finished product.

This project remains planned. A one-day probe must find the fewest effective fields and checks, then pass the Kotlin regression and valid controls before runtime work begins.

## Problem and Users

Delano checks a project against its written scope. The Kotlin scope called agent supervisors its users and removed the transcript, response, and creation paths they needed. Validators still saw the required headings, dependencies, evidence, and tests. Parent status could close with the scoped tasks. No command asked a human to run the supervision workflow.

This project serves four people:

- Owners approving scope and spend.
- Operators deciding whether to continue, reshape, or stop.
- Agents and engineers who need authority to halt drift.
- Human reviewers deciding whether the running result is useful enough to close.

## Outcome and Success Metrics

Before activation, a meaningful project shows the user, job, newly possible action, deliberate omissions, and exact steps that prove the claim on realistic data. The same walkthrough decides continuation and closeout.

### Walkthroughs this project must pass

- DEMO-001: Load the sanitized Kotlin project as new Mode 4 product work. Activation refuses it because its walkthrough cannot supervise an agent, or the owner reshapes it.
- DEMO-002: Classify that work as infrastructure. Delano states that no end-user action changes, names the downstream action, and requires owner acceptance.
- DEMO-003: Plan a corrected product. A thin supervision loop on representative data comes before broad foundations. Every later task supports a walkthrough step or states why it must come first.
- DEMO-004: Complete substantial foundations without another critical step working. The mid-project check returns reshape-required or stop and blocks unrelated starts.
- DEMO-005: Close the read-only shell with passing tests and screenshots. The real-data walkthrough still cannot read an agent message, create work, or respond, so closeout refuses.
- DEMO-006: Run honest infrastructure, a valid product slice, a Mode 0 patch, a Mode 1 change, and legacy projects through their intended paths.

### Measures

- SM-001: New Mode 2 through 4 projects cannot activate until the five facts, classification, surface, human decision, and any required probe agree with the original request or roadmap outcome and touched files. Genuine Mode 0 and 1 work stays light.
- SM-002: product, infrastructure, and mixed all have valid paths. Infrastructure never claims an immediate end-user action and always records the downstream user action and owner acceptance.
- SM-003: Product and mixed work cannot expand into broad foundations until a human uses an early job-critical slice on representative data, unless the owner reshapes the project.
- SM-004: Every planned value checkpoint records which critical and supporting walkthrough steps actually work. Missing the expected critical step after material groundwork produces reshape-required or stop and blocks unrelated starts.
- SM-005: Product closeout fails when the job cannot be completed on representative real data or a critical human finding remains open, regardless of automated evidence.
- SM-006: The Kotlin case and its polished, schema-complete, and screenshot-complete variants produce no false pass at activation, mid-project review, or closeout. Infrastructure, valid product, small-mode, and legacy controls produce no false block.
- SM-007: Affected contracts, skills, runtime output, fixtures, docs, generated/package files, and release checks agree.

## User Stories

- US-001: Owners see the user, job, action, omissions, and walkthrough before funding work.
- US-002: Infrastructure owners approve groundwork without claiming a user change.
- US-003: Executors prove a thin loop early and justify larger foundations.
- US-004: Supervisors and executors stop when the approved job is unreachable.
- US-005: Reviewers judge the real workflow; automation supports that judgment.
- US-006: Maintainers adopt the rules without burdening patches or rewriting history.

## Acceptance Scenarios

- AC-001: Given a new Mode 2 through 4 project has a missing or conflicting user, job, new action, omission, classification, surface, walkthrough, required probe, or human decision, activation fails before any state write and names the problem. Claims must agree with the original request or roadmap outcome and touched surfaces.
- AC-002: Given honest infrastructure work, activation states that no end-user action changes, names the downstream user action it is intended to unlock, records owner acceptance, and never presents the infrastructure project itself as product success.
- AC-003: Given product or mixed work, the plan first lets the user see relevant state, act, and get a useful result on representative data. A human reviews that loop. Every task makes a walkthrough step work or states which step it enables and why.
- AC-004: Given a supporting task is complete, only a walkthrough step actually run in its declared environment counts as user progress. Setup, schemas, tests, polish, and screenshots cannot satisfy a checkpoint that expects a job-critical step.
- AC-005: Given a named value checkpoint is reached, Delano compares the working walkthrough with the prior checkpoint and records evidence plus continue, reshape-required, or stop.
- AC-006: Given scope can no longer deliver the job, or material groundwork adds no expected critical step, any executor or supervisor stops and reports it. Unrelated starts stay blocked until the owner decides.
- AC-007: Given product or mixed work reaches closeout, a named human runs every walkthrough step on representative real data and records pass or fail for the intended job, usefulness, information hierarchy, copy, contextual actions, data quality, and interaction.
- AC-008: Given accessibility, performance, integration, test, or screenshot evidence passes while the walkthrough or human review fails, closeout fails. The automated evidence remains visible as supporting proof.
- AC-009: Given the Kotlin fixture or a polished, schema-complete, screenshot-complete, or combined variant, activation reshapes it or reclassifies it as infrastructure with the required disclosure, the mid-project check stops unchanged user capability, and product closeout rejects it. Valid product and infrastructure controls pass.
- AC-010: Given a bounded Mode 0 patch or Mode 1 change, normal commands add no value artifact or product review beyond existing local risk rules. A new multi-step capability, coordinated slices, material uncertainty, or cross-surface change labeled Mode 0 or 1 must escalate to Mode 2 or higher.
- AC-011: Given an upgrade, complete and deferred history validates unchanged, planned Mode 2 through 4 projects migrate before activation, and active projects migrate at their next value checkpoint with no silent close.
- AC-012: Filling every field, adding polish and screenshots, renaming machine work, splitting one job into trivial steps, or self-asserting approval cannot pass unless the job runs and the human decision is valid.

## Scope

### Required

- Put the user, job, new action, omissions, classification, surface, and walkthrough in the project files. Enforce them at activation, during delivery, and on every close path.
- Require a thin human-reviewed loop before broad foundations. Show the current decision and required human action in status, next-work, and Viewer.
- Ship the Kotlin regression, gaming variants, valid controls, migration rules, agent evaluations, and release evidence.

### Classifications

- product promises a new end-user action and proves the critical loop.
- infrastructure promises a technical capability, states that no user action changes yet, names the downstream action, and requires owner acceptance.
- mixed does both. Each part follows its own rule.
- Each project also identifies the changed surface as none, ui, cli, api, workflow, or mixed. The value must agree with the original request or roadmap outcome and actual touchpoints. none cannot hide work that changes a human interface or workflow.

An action required by the original job can move into omissions only through an owner-approved outcome change or an honest infrastructure reclassification.

This project's classification and surface are both mixed. It changes contract and runtime policy plus operator-facing CLI, status, and Viewer behavior. Its first usable proof is DEMO-001: Delano stops a project that would currently validate and tells the owner which user action is missing.

### Optional

Small cleanup to updates, prose, naming, Viewer convenience, or wording checks may ship only when it supports a gate.

### Out of scope

- Repairing or continuing the Kotlin app.
- Banning foundation, security, persistence, transport, performance, or reliability work.
- Requiring a GUI, prescribing a visual style, or assigning a universal UX score.
- Treating screenshots, line counts, task counts, file counts, word bans, or a model's opinion as proof of user value.
- Cryptographic identity, organization-wide authorization, remote tracker writes, public approvals, production deployment, or unrelated cleanup.

## Functional Requirements

- FR-001: New Mode 2 through 4 specs use a versioned product, infrastructure, or mixed classification and a surface value of none, ui, cli, api, workflow, or mixed. They record the original request or roadmap outcome, user, job, new action, omissions, walkthrough, and infrastructure's downstream user action.
- FR-002: Activation validates the current contract, probe state, classification, surface, and owner or reviewer decision before writing state. The approval must identify the current spec content it covers.
- FR-003: The planned boil-it-down skill runs before activation, at value checkpoints, and before closeout. It challenges spec.md and plan.md, removes unjustified work, and stops when the job or walkthrough is not credible. Another report cannot resolve failure.
- FR-004: For every surface other than none, product and mixed plans name the checks that surface needs. UI, workflow, and mixed work cover information hierarchy, copy, contextual actions, realistic data and states, interaction feedback, and empty, loading, and error behavior. A human reviews the early critical loop before broad foundations. Groundwork scheduled first explains why and how much.
- FR-005: Job-critical steps are required to complete the user's job. Supporting steps only prepare or enable them. Tasks keep stable step links and a role of vertical-proof, enablement, product-quality, or adoption. Enablement alone never advances the walkthrough or satisfies a critical step.
- FR-006: Each mid-project check runs the walkthrough in its listed environment, compares it with the prior result and expected critical steps, records what happened, then decides continue, reshape-required, or stop. Unresolved or failed decisions block unrelated starts.
- FR-007: AGENTS and the discovery, planning, execution, quality, and closeout skills give every executor and supervisor authority and a duty to stop when approved scope cannot deliver the job.
- FR-008: Status, next-work, and Viewer show classification, working critical and supporting steps, the latest decision, blockers, and the human action needed. Task completion alone is never user progress.
- FR-009: Product closeout requires the walkthrough on representative real data and a named human's judgment of job completion, usefulness, information hierarchy, copy, contextual actions, data quality, and interaction. Every close path blocks on a critical finding.
- FR-010: Infrastructure closeout verifies the promised technical capability and restates the downstream user action. It creates no product review or product-success claim.
- FR-011: Fixtures cover the Kotlin failure; polished, schema-complete, screenshot-complete, combined, and trivial-step variants; honest infrastructure; valid product; real Modes 0 and 1; and planned, active, complete, and deferred legacy projects.
- FR-012: Deterministic tests check contract and lifecycle behavior. Agent evaluations check whether an eager executor stops or reshapes. A human decides whether the product works well enough. Release requires every applicable evidence type.
- FR-013: New projects use the versioned rules by default. Planned projects migrate before activation, active projects at the next checkpoint, and terminal history stays readable. Migration preserves user content and never invents approval, progress, or findings. Mode selection rejects coordinated or material work split into fake Mode 0 or 1 changes.
- FR-014: Source contracts, .agents files, runtime, tests, docs, Viewer, generated .claude mirror, package payload, and npm package remain synchronized.

## Non-Functional Requirements

- NFR-001: Missing, stale, or failed gate state makes lifecycle commands refuse the change before writing any project state.
- NFR-002: Deterministic validation stays local, repository-relative, privacy-safe, and linear in the number of project artifacts.
- NFR-003: Models and keyword checks may advise. They cannot be the only enforcement of user value.
- NFR-004: Human review records short findings and the exact content, build, data, and walkthrough reviewed. It does not require an essay or numeric taste score.
- NFR-005: Recurring effort stays below the cost of the failure. Modes 0 and 1 gain no mandatory artifact family.
- NFR-006: Tests and other invisible engineering evidence remain valid and visible when a product gate stops further work.

## Assumptions

- An eager, compliant agent will preserve the original request or roadmap outcome and will not self-approve a human decision. Markdown cannot make a malicious writer with full repository access honest.
- Representative data may be local, staged, or production-derived. It must reproduce the data shape, scale, states, and failures named in the walkthrough.
- Infrastructure can be valuable without an immediate product surface when the owner accepts that limit explicitly.
- Existing dependency and scoped lifecycle machinery can carry the new checks without adding another top-level status model.

## Needs Clarification

- NC-001: How approval is tied to current work. Current recommendation: record a named owner or delegated human and bind approval to the current spec, perhaps with a content hash. Closeout also records the build, data, and walkthrough reviewed. A display name is not authenticated identity. The probe decides the exact mechanism.
- NC-002: When mid-project checks run. Current recommendation: use each checkpoint named in the plan and each workstream handoff, plus an immediate stop whenever scope drift is found. Avoid fixed task counts and time quotas.
- NC-003: Whether infrastructure may start without a scheduled downstream product. Current recommendation: allow it only when the owner accepts that no user action changes yet and the intended downstream action is named. Never call that project product success.
- NC-004: Who may review. Current recommendation: the owner or a delegated human may review; the implementing agent may not self-approve. High-risk work should use a non-implementing reviewer when one is available.

## Hypotheses and Unknowns

- H-001: A literal walkthrough plus deliberate omissions will expose a missing user job earlier than broad outcome prose.
- H-002: Checkpoints tied to expected critical steps will stop drift better than task-count or time-based quotas.
- H-003: Contract checks, lifecycle blocks, agent behavior tests, and human review together will resist paperwork gaming.
- U-001: The probe must find the fewest fields needed to save a review or checkpoint and tie it to current content, build, and data.
- U-002: Agent evaluations must distinguish a real stop from a warning followed by continued execution.
- U-003: The minimum useful CLI/status/Viewer display remains undecided. This project must not become a dashboard redesign.

## Footguns Discovered

- Required headings can exist while the user's job is absent.
- Checked criteria and proof-like text can close tasks around a useless product.
- Final-task rollups can close parent state, so every close path needs the same refusal-before-write check.
- infrastructure and none become escape hatches unless they are checked against the original request and touched files or screens.
- Screenshots can prove that the wrong interface rendered correctly.
- A checkpoint is useless if setup counts as user progress or a failed decision does not block work.
- A display name and content hash do not authenticate a person or prove which running build was reviewed.
- A new payoff file, language ban, or update limit would add easy paperwork and weak protection.
- Large work can evade the gates if coordinated slices are mislabeled Mode 0 or 1.

## Remaining Unknowns

NC-001 through NC-004 and U-001 through U-003 remain open. The probe may change storage, field names, and command shape. It may not weaken activation, mid-project stop authority, the real-data walkthrough, migration protection, or human closeout judgment.
