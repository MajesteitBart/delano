# Findings: User value gate and product quality design

## Conclusion

Delano needs a lifecycle-level user-value control, not a new writing exercise. The safe design makes the intended job and demo part of canonical scope, sequences a thin vertical proof before broad foundations, blocks progress when re-boil shows no working capability gain, and requires a human product review on representative data before closeout. Infrastructure remains valid under an honest classification and first felt-value boundary.

The enforcement must be layered. Structure and lifecycle checks catch omissions and stale gates. A short `boil-it-down` skill challenges incentives and authorizes stopping. Behavioral fixtures test whether an eager agent actually stops instead of expressing concern and continuing. A human judges whether the running product is useful and coherent. This is more resistant to gaming than a line-capped payoff file, keyword bans, screenshots, or evidence volume.

## Observations

### O-001: The Kotlin project conformed to a scope that excluded its user's job

The foundation spec explicitly deferred transcript, input, new-task, and creation workflows while naming people who supervise agents as users. The resulting app could browse environments, projects, and thread names but could not show what an agent said, create work, or respond. Delano had no activation gate that forced those two facts into one decision.

### O-002: The visible defects were in scope, but automated quality optimized the wrong layer

The real-server surface showed a global context-insensitive Add action, raw identifiers, repeated titles, broken plurals, redundant environment labels, meaningless badge colors, and status/lifecycle values stuck at Unknown. Accessibility, race, integration, performance, and closeout evidence did not expose the information-architecture and usefulness failure.

### O-003: The invisible engineering remains legitimate

Transport, persistence, reconciliation, connection supervision, idempotency recovery, and credential handling are useful assets. The intervention must not ban them. It must force an honest answer about what new user capability they enable, how much is proportionate before vertical proof, or whether the project is infrastructure with payoff deferred.

### O-004: Current validators prove conformance, not value

Operating-mode checks require headings and artifact kinds. Contract validation checks core frontmatter and dependencies. Done-task evidence checks marked criteria and proof-like evidence text. These are appropriate deterministic checks, but an eager agent can satisfy all of them while the intended user job remains impossible.

### O-005: Current lifecycle rollups can close around a product gap

Native task close/defer rolls parent workstream and project state when no open tasks remain. Closeout guidance asks for an outcome review, but product-demo/human-review failure is not a precondition on every mutation path. The new closeout gate must be inside lifecycle semantics, not a report written after the project has already become complete.

### O-006: Existing review provenance is useful but not a human/build trust boundary

Published reviews bind comments to a Markdown source content hash and optional display name. That can inspire current-content approval, but it does not authenticate the reviewer or prove what running build and data were exercised. The new contract must state that limitation instead of claiming machine-proof human judgment.

### O-007: The strategy-layer precedent shows the right contract discipline

The strategy project recorded adversarial findings, rejected unsafe designs, derived rather than duplicated relationships, separated source work from generated integration, and mapped final acceptance to evidence. This project should reuse that discipline while adding the missing real-user/job and human-product evidence dimensions.

### O-008: Pocock's strongest contribution is interaction shape, not copied rules

`grill-me` is a tiny front door into relentless inquiry, `wait-what` stops and re-pitches a message that did not land, and `prototype` builds only enough throwaway behavior to answer one question. The relevant pattern is short, direct, action-oriented intervention with an explicit stop, not their wording or file layout.

### O-009: The proposed `boil-it-down` concept has the right checkpoints but gameable mechanics

Named capability, literal demo, boring version, honest infrastructure disclosure, re-boil, and product/taste closeout directly address the failure. A 30-line cap, banned vocabulary, screenshot requirement, and update-file limit do not. An agent can rephrase machine output as human value, photograph a useless screen, or compress ceremony without making the job possible.

## Kotlin Regression Oracle

The formal future fixture must preserve these facts:

- Stated user job: supervise agents from a native Android client.
- Approved scope: foundation plus read-only environment/project/thread browsing; transcript, response, and creation deferred.
- Substantial passing evidence: protocol/data/reconciliation/supervision/idempotency/credential work, tests, instrumentation, and closeout machinery.
- Representative server shape: one environment, dozens of projects, hundreds of threads, and a selected thread.
- Delivered behavior: no transcript/messages, no create/respond path, global Add means add environment, raw IDs, repeated titles, broken plurals, redundant labels, and Unknown status/lifecycle.

Expected decisions:

1. Activation: reject as a product scope or require honest infrastructure disclosure plus a named first felt-value boundary.
2. Re-boil: after material foundation completion with no newly working supervision step, return `reshape-required` or `stop` and block unrelated continuation.
3. Closeout: fail product acceptance even when automated gates and screenshots pass.

Gaming variants must fix cosmetic text, fill every schema field, attach screenshots, and relabel foundation tasks as value. They must still fail because the representative supervision job is not executable.

The adversarial review also requires a trivial-step variant: splitting the demo into setup/navigation fragments must not unlock foundations when the boundary's expected job-critical state-action-result loop is still impossible.

## Adversarial Outline Review

The outline was attacked as if an eager agent wanted to preserve the Kotlin delivery while satisfying every new field. Each repair changes a lifecycle decision or behavioral oracle; none is satisfied by producing more prose.

| Attack | False-pass path | Contract repair and expected behavior |
| --- | --- | --- |
| Redefine supervision as browsing | Name navigation as the capability and move transcript/respond/create to non-capabilities | Bind the value contract to upstream intent and visible touchpoints. An essential job capability can move only through owner-approved outcome change or honest infrastructure reclassification; product activation otherwise fails. |
| Split a useless demo into plausible steps | Count connection, navigation, list rendering, or selection as incremental user value | Tag steps as `job-critical` or `supporting`; require an early state-action-result loop on representative data. Supporting steps never satisfy a boundary expecting a critical step. |
| Rename foundations as value | Map every transport, persistence, or test task to a demo label | Only execution of the representative demo changes working-capability progress. Enablement needs a bounded rationale and proportionality; no critical progress at a declared boundary produces `reshape-required` or `stop`. |
| Polish evidence without adding the job | Fix copy, fill status fields, attach screenshots, and pass accessibility/integration tests | Closeout reruns the literal job on representative data and requires non-self-approved human product judgment. Supporting evidence remains visible but cannot override a failed demo or critical finding. |
| Hide a product surface | Declare `surface: none` while tasks still touch UI/workflow behavior | Classification and surface profile must agree with upstream intent and touched surfaces. Activation and behavioral fixtures reject the contradiction. |
| Launder scope through small modes | Slice one coordinated product capability into Mode 0/1 tasks to avoid the full contract | Keep small-mode artifacts light only for genuinely bounded work; mode selection/readiness escalates multi-step capabilities, related coordinated slices, material uncertainty, and cross-surface work to Mode 2+. Positive controls protect real patches. |
| Self-assert a passing gate | Have the implementing agent write a plausible approval or product review | The agent cannot self-approve a human gate. Evidence names an accountable reviewer and binds to current content/build/data while explicitly not claiming cryptographic identity. |
| Close through a different mutation path | Use final-task rollup or direct Markdown edits instead of the normal close command | Close preconditions apply to project close, task/workstream rollups, validation, and Viewer-triggered lifecycle paths, with failure-before-write semantics. |

Against the unchanged Kotlin regression, an eager compliant agent therefore has two honest paths before execution: restore a job-critical supervision loop to the product scope, or classify the work as infrastructure and disclose zero immediate user capability. If it nevertheless advances foundations without that loop, re-boil blocks unrelated starts. If it reaches closeout, the representative supervision demo and human product review fail. Shipping the same read-only shell as a successful product cannot satisfy all three gates.

## Options Considered

| Option | Pros | Cons | Decision |
| --- | --- | --- | --- |
| Mandatory line-capped `payoff.md` | Easy to see and validate | New compliance artifact; parallel truth; easy to game | Reject |
| Add value sections only | Low artifact overhead | Presence checks alone remain weak | Use as canonical base, not sole defense |
| Automated semantic/LLM approval | Can flag vague or machine-facing prose | Nondeterministic; can be prompt-shaped; cannot replace ownership | Advisory/evaluation only |
| Screenshots or recordings as hard proof | Concrete visual evidence | Can faithfully show the wrong product | Supporting evidence only |
| Ban foundation-heavy projects | Prevents one failure mode | Destroys legitimate infrastructure and reliability work | Reject |
| Layered lifecycle, skill, behavior, and human gates | Tests omission, action, and real product quality | Cross-cutting; needs migration and clear trust language | Choose |

## Fold-Forward

- `spec.md` now defines the value contract, three delivery classifications, literal Delano demo, mandatory and optional scope, failure behavior, Kotlin regression, compatibility, probe, and owner decisions.
- `decisions.md` records the layered design and rejects artifact-count/keyword/screenshot proxies.
- `plan.md` sequences activation, value-first execution, product closeout, regression/adoption, and release work with explicit rollback and evidence classes.
- Four workstreams and twelve planned tasks separate contracts, supervision, product review, and integration while preserving acyclic dependencies.

## Open Questions

- Approval provenance and the explicit limit of local human identity claims.
- Stable plan syntax for value-risk boundaries.
- Activation policy for unscheduled downstream payoff from infrastructure.
- Reviewer independence at solo versus multi-person scale.
- Smallest decision-record shape that stays content-current without becoming a new source of truth.

These questions and the behavior probe block activation, not contract outlining.
