# Discovery

Use the [writing and scope guidance](../../references/output.md). Read [delivery contracts](../../references/contracts.md) when changing project files.

Read the request, existing spec, relevant code or product evidence, and decisions already made. For a small fix with clear acceptance, update the existing task and continue the requested work. Reopen discovery only for a question that could change the outcome or scope.

Describe who has the problem, what happens today, what should change, and how someone could judge the result. Use actual measurements when available. Label proposed targets and untested assumptions. Ask only questions whose answers affect the work; make reasonable, reversible assumptions explicit and continue independent work.

Update `spec.md` using the repository's template or the bundled [spec](../../assets/templates/spec.md) when a project needs one. Keep scope boundaries and acceptance scenarios concrete. Preserve an existing roadmap link and read the item's intent. Record approval only when the user has supplied it.

Decide whether an unknown needs research or a prototype. Research checks facts or options; a prototype tests behavior. Name the decision the investigation would change. If existing evidence supports the approach, record why the probe can be skipped.

## Result

Lead with the proposed outcome and scope. Follow with the evidence behind them and any unresolved question that changes the next step. Link the updated spec. Keep a brief request brief; omit a discovery report when the existing task already says enough. If the user also authorized implementation and the scope is settled, continue.
