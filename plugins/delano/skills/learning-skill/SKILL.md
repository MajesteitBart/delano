# Delivery learning

Use the [writing and scope guidance](../../references/output.md). Read [delivery contracts](../../references/contracts.md) when recording decisions or follow-up work.

Start with the requested question and relevant task evidence, decisions, reviews, or incident. Use measurements that exist and explain what they measure. Completion counts alone say little about the outcome for users.

Describe what happened, its consequence, and the evidence for the suspected cause. Consider plausible alternative explanations. Distinguish a single incident from a recurring pattern. Include what worked when it affects the proposed change.

Choose the smallest supported improvement. Removing a redundant step may help more than adding a rule. Other useful changes include clarifying an instruction, fixing an executable check, or making a template's example concrete. Judge each by the problem it would solve, maintenance it adds, and evidence that would show whether it helped.

Record the proposal in an existing decision, task, or closeout note. Create a follow-up task when implementation belongs to the agreed scope. If the user requested the improvement, carry out the supported change and run relevant checks. A request for reflection alone produces recommendations.

Preserve superseded decisions and their rationale. Keep a local workaround scoped to the conditions that required it. If evidence supports no change, say so. Avoid creating an improvement backlog, telemetry system, or new process requirement to give the retrospective an output.

## Result

State the observed problem, the proposed or completed change, and how its effect can be judged. Link the evidence and name remaining uncertainty. A short observation can stand alone. Skip generic lessons such as "communicate better," maturity scores without a defined measure, and praise that explains no result.
